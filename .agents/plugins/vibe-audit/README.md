# vibe-audit

목적별로 범위를 좁힌 **읽기전용 감사자 6종**.

공장은 품질부서를 생산부서에서 떼어 놓고, 감사를 목적별로 쪼갭니다. ISO 심사원은 화학사고 위험을 보지 않고, PSM 점검원은 고객 도면 관리를 보지 않습니다. 시야가 좁게 설계되어 있어서 깊게 봅니다.

이 플러그인은 그 두 가지를 코드 감사에 옮긴 것입니다.

## 왜 에이전트인가

각 감사자의 프론트매터에는 이렇게 적혀 있습니다.

```yaml
tools: ["Read", "Grep", "Glob"]
```

`Edit` · `Write` · `Bash` 가 **없습니다.** 고치라고 시켜도 못 고칩니다.

"감사자는 고치지 않는다"를 문서에 쓰는 것과, 애초에 설비 열쇠를 주지 않는 것의 차이입니다. 스킬로는 지시밖에 못 하고 지시는 세션 분위기에 따라 흔들립니다 — 부적합을 찾고 나서 "이건 한 줄이니 바로 고칠게요"가 나오는 구조입니다. 도구 제한은 지시가 아니라 구조입니다.

감사자가 고친 코드는 **아무도 검사하지 않은 코드**가 됩니다.

## 감사자 6종

| 이름 | 무엇만 보는가 | 현장 대응 |
|---|---|---|
| `audit-secrets` | 시크릿 · 자격증명 · 환경 분리 · 권한 경계 | ISO 27001 |
| `audit-data` | 스키마 · 마이그레이션 · 트랜잭션 · 되돌림 | 설비 변경 관리(MOC) |
| `audit-quality` | 테스트 · CI 게이트 · 평가셋 — 검사 장치 자체 | ISO 9001 |
| `audit-ops` | 로깅 · 관측 · 알림 · 롤백 · 인시던트 경로 | 가동전점검(PSSR) · 비상조치 |
| `audit-contract` | 공개 API · 응답 형식 · 하위 호환성 | 고객사 감사(2자) |
| `audit-internal` | 문서에 적은 규칙 대비 실제 코드 | 자체 감사(1자) |

여섯이 보는 범위는 겹치지 않습니다. 각 감사자의 「보지 않는 것」 절에 담당이 명시되어 있어, 범위 밖을 발견하면 적지 않고 담당만 넘깁니다.

## 설치

대화형 세션은 마켓플레이스에서:

```bash
claude plugin marketplace add pdw96/claude-kit
claude plugin install vibe-audit@pdw96-kit
```

클라우드 레인은 이 경로를 받지 못한다. 그 레포의 `.claude/agents/` 에 사본이 있어야 한다 — `scripts/sync-agents.sh` 와 저장소 뿌리 README 참고.

## 쓰는 법

```
@audit-secrets backend/app 아래만
@audit-data 이번 PR 의 마이그레이션
@audit-quality 저장소 전체
```

또는 새 세션으로:

```bash
claude --agent audit-ops
```

**한 번에 하나씩** 돌리세요. 여섯을 한꺼번에 돌리면 전부 얕아집니다 — 범위를 좁히는 것이 이 플러그인의 전부입니다.

감사 대상 코드를 방금 이 세션에서 작성했다면 **새 세션에서 돌리세요.** 자기가 세운 전제를 그대로 들고 검사하게 됩니다.

## 결과를 어떻게 다루나

각 감사자는 번호 매긴 부적합 목록(`NC-1`, `NC-2` …)과 **「안 본 것」**을 냅니다. 안 본 것이 결과의 일부입니다 — 이게 없으면 "감사했으니 괜찮다"는 잘못된 안심이 생깁니다.

부적합은 파일이나 이슈로 남기세요. 등록되지 않은 "나중에 고쳐야지"는 예외 없이 사라집니다.

그리고 공장에서 부적합을 닫는 권한은 "고쳤다"가 아니라 **유효성 검증**에 있습니다. 고친 뒤 **같은 감사자를 다시 돌려** 재발하지 않았는지 확인할 때 닫습니다. 포스트모템 액션 아이템이 무력해지는 지점이 정확히 여기입니다.

그래서 **기록을 `.claude/audits/<감사자 이름>-<날짜>-<시각>.md` 로 남기세요** — 시각은 초까지 붙이고, 같은 이름이 이미 있으면 덮지 말고 끝에 `-2` 를 붙입니다. 고친 뒤 같은 날 다시 돌린 기록이 앞의 것을 덮으면 다음 회차가 이을 번호가 사라집니다. 레포가 대장을 따로 두었으면(`CLAUDE.md` 등이 가리키는 곳) 그 대장에 등록하고, 감사자도 그 대장을 지난 기록으로 읽습니다. **한 작업트리에서는 감사를 하나씩 돌리세요 — 감사자가 달라도** — 브리핑 자리(`.claude/audit-brief.md`)가 하나라 서로의 것을 덮고, 같은 지난 기록을 읽으면 같은 다음 번호를 뽑아 서로 다른 결함에 붙입니다. 감사자는 쓰는 도구가 없어 스스로 남기지 못합니다. 다음 회차의 같은 감사자가 이 폴더에서 자기 이름이 붙은 가장 최근 기록을 찾아 NC 번호를 잇습니다 — 지난 NC-1 이 그대로 있으면 이번에도 NC-1 이고, 해소된 번호는 은퇴해서 다른 결함에 다시 가지 않습니다.

그리고 지난 NC 가 이번 목록에 없을 때 **「해소」와 「이번엔 안 봄」을 가릅니다.** 해소는 고쳐진 자리를 이번에 직접 본 경우이고, 범위 밖이라 안 본 것은 안 본 것으로 남습니다. 둘을 섞으면 「안 본 것」을 두는 이유가 시간 축에서 그대로 무너집니다 — 안 본 자리가 고쳐진 자리로 기록됩니다.

## 감사 계획과 부적합 대장

이 플러그인은 개별 감사만 합니다. 부적합을 재감사로 닫힐 때까지 따라가는 대장은 `vibe-slice` 플러그인의 틀(스킬 `slice-docs` 의 `templates/`)을 베껴 세웁니다 — 감사자는 그 대장을 `CLAUDE.md` 가 가리키면 지난 기록으로 읽습니다. 언제 돌릴지는 조각 요구사항 「제약」의 감사 회차가 정합니다 — 고르는 법은 claude-kit [절차 지도](https://github.com/pdw96/claude-kit/blob/main/docs/procedure.md)의 「감사 회차」입니다. 아래 표는 그 원천 가운데 하나(바뀐 것 → 감사자)입니다.

대략의 주기:

| 시점 | 돌릴 감사자 |
|---|---|
| 앵커볼트 층을 건드린 PR | `audit-data`, `audit-secrets` |
| 공개 API 를 건드린 PR | `audit-contract` |
| 첫 배포 직전 | `audit-ops`, `audit-quality` |
| 조각 서너 개 머지한 뒤 | `audit-internal` |
| 장애 후 | `audit-ops` → 고친 뒤 다시 `audit-ops` |

## 이 감사자들은 감사받는가

`audit-quality` 가 남에게 요구하는 것을 이 플러그인이 자기 자신에게 적용한
자리가 `evals/` 입니다.

```bash
./scripts/run-evals.sh
```

케이스 스물다섯이 셋을 잽니다.

| 무엇 | 케이스 | 재는 것 |
|---|---|---|
| 판정 | 열다섯 | **오검율**과 판정의 근거. 실제 되먹임에 붙은 다섯(로컬 개발 비밀번호 · 라이브니스 프로브 · 롤백 흔적 · 담당 밖 NC · 담당인 것 넘기기)과 사본 비교에서 온 넷(운영 표를 잠그는 마이그레이션 · 주석에만 적힌 결정 · 읽어서 단정한 「무엇을 잡는가」 · 밖에서 보이는 권한 실패)에, 브리핑이 있을 때와 없을 때 둘 · 회차 잇기(첫 회차 · 이어지는 회차) 둘 · 담당 없는 발견 하나 · 조각 폴더의 범위(닫힌 조각 · 옛 `PRD.md`) 하나 |
| 트리거 | 열 | 부른 감사자가 뜨는가, 부르지 않은 셋이 제 자리에서만 뜨는가, `audit-ops` 는 청하지 않으면 안 뜨는가, 무관한 요청에 아무도 안 뜨는가 |

거짓 지적을 두어 번 내면 아무도 감사자를 안 부르므로, 이 도구에서 가장 비싼
결함이 오검입니다. 판정 케이스의 픽스처에는 **진짜 부적합이 하나씩** 들어
있습니다. 아무것도 안 내는 감사자가 만점을 받는 것을 막는 대조군입니다.

`./scripts/run-evals.sh` 는 인자 없이 스물다섯을 다 돌립니다. PR 의 CI 는 트리거
열만 문턱 1.0 으로, 전수는 `workflow_dispatch` 로 문턱 0.8 에서 돌립니다.

자세한 것은 `evals/README.md` 「케이스」 · 「재는 법」.

## 한계

- 감사자는 **읽기만** 하므로 테스트를 돌려보지 못합니다. 실행이 필요한 검증은 CI 쪽 일입니다.
- **셋은 요청하지 않아도 뜹니다.** `audit-secrets` 는 인증 · 권한 · 환경변수 · CORS · API 키를 건드렸다는 말이 나오거나 코드에 키가 박혀 있으면, `audit-contract` 는 응답 필드 · 에러 규약 · SDK 를, `audit-data` 는 스키마 · 마이그레이션을 바꿨다는 말이 나오면 — 묻는 것이 다른 일이어도 답하기 전에 돌아갑니다. 그만큼 **모델 사용량과 지연이 늡니다.** 원치 않으면 그 감사자의 `description` 에서 해당 문장을 지우세요(사본은 그 레포 것이니 고쳐도 됩니다). 재는 법은 `evals/README.md` 「트리거 정확도」.
- 나머지 셋(`audit-internal` · `audit-ops` · `audit-quality`)은 부르지 않으면 뜨지 않습니다 — 바쁠 때 안 부르게 되는 구조라, 중요한 검사는 결국 CI 게이트로 옮겨야 합니다. `audit-quality` 가 그 자리를 찾아 줍니다.
